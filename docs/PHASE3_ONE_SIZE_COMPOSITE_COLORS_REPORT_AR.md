# Phase 3 — المقاس الموحد والألوان المركبة

## الحالة وحدود التنفيذ

التغييرات محلية على `arena/740f973f-vetrina-app` للمراجعة. لا Commit ولا Push ولا نشر Vercel. لم يُطبّق ترحيل المرحلة الثالثة على Live، ولم تُكتب بيانات اختبار فيه. أُجري استعلام قراءة للميتا فقط للتأكد من أنواع وقيود `product_variants`: اللون والمقاس من نوع text، ولا يوجد قيد مقاسات يحتاج إلى توسيع.

## تصميم البيانات

- `ONE_SIZE` قيمة تقنية في عمود size الموجود، وعرضها «مقاس موحد». لم يتغير نوع العمود ولم تُحوّل أي قيمة قديمة.
- ترحيل إضافي: `supabase/migrations/202611130027_product_attributes.sql`، دون تعديل الترحيلات السابقة.
- عمود `color_components text[] NULL`؛ NULL للبيانات القديمة غير المنظمة، عنصر واحد للون المفرد الجديد، و2–6 للألوان المركبة.
- حد اسم المكون 40 محرفاً؛ يمنع الفراغ والمحارف الضابطة وNULL والتكرار. إزالة المسافات ASCII الطرفية مقصودة لتتطابق مع btrim الافتراضي في SQL؛ لا توجد محاولة لتوحيد تهجئة أسماء مختلفة.
- الترتيب حتمي حسب Unicode scalar/UTF-8 COLLATE C، دون الاعتماد على لغة المتصفح. عرض اللون من جمع المكونات بـ ` / `، وهو ليس مفتاح الهوية المنظم.
- لا تقسيم لأسماء الألوان القديمة، ولا backfill، ولا تغيير لهويات المنتجات أو التركيبات أو الباركودات.
- قيد CHECK يتحقق من الترتيب المعياري وتطابق اسم العرض للحقل المنظم، دون رفض صفوف NULL القديمة.
- تحديث `engine_create_product_atomic` بنفس التوقيع والصلاحيات؛ التحقق والتوليد من الخادم، مع قبول الطلبات القديمة دون الحقل. يرفض تكرار المجموعة/المقاس وعكس ترتيبها وكذلك اصطدام اسم العرض داخل الطلب.
- المنتج والتركيبات والمخزون والباركودات ضمن المعاملة نفسها. رفع Storage ليس جزءاً من معاملة SQL.

## الواجهة

- خيار «مقاس موحد» في CustomSelect، بعمود كمية واحد لكل لون.
- تأكيد صريح قبل مسح كميات/باركودات عند تغيير نوع المقاس؛ الإلغاء يحافظ عليها.
- نوع اللون: مفرد أو مركب باستخدام CustomSelect. مكونات اللون المركب تُختار تباعاً من درج القائمة الداكن نفسه، مع عرض الأسماء وأزرار إزالة، لا قائمة HTML أصلية.
- لإنشاء مكوّن غير موجود: اكتب اسمه في حقل اللون ثم اختره من قائمة المكونات. لونان على الأقل قبل إضافة اللون المركب.
- الصف المركب واحد، والكمية وباركود التركيبة واحد لكل مقاس؛ لا توزيع للمخزون بين المكونات.
- لا حقول إلزامية تجارية إضافية. تأكدت اختبارات DOM من وصول مصفوفة المكونات وONE_SIZE والكمية إلى RPC الحالي.

## تكامل الباركود والمخزون

- لا نوع باركود جديد؛ الربط بقي عبر variant_id. لم تتغير مولدات/حراس الباركود أو سجل المطالبات.
- باركود الموديل يفتح اختيار اللون/المقاس فارغاً ويتطلب التأكيد، حتى للون مركب بمقاس موحد واحد.
- باركود التركيبة وUUID يحلان إلى الهوية نفسها، مع صافي المخزون الحالي.
- القراءة في POS والمنتجات والطباعة تشمل المكونات. كاش الكتالوج يحفظ الكائنات كما هي؛ الحقل اختياري، والاسم القديم يبقى fallback دون إعادة تفسير. لم يتغير منطق أولوية السجل المتصل على الكاش.
- ترجمة المقاس في خيارات POS والسلة والملصقات والإيصال النصي وHTML والوصف المولد؛ يبقى الكود التقني في البيانات.
- لم تُعدّل دوال الحجز أو المخزون الذري أو جداول orders أو RLS أو الصلاحيات القديمة. المساعد الجديد ليس SECURITY DEFINER، وصلاحية استدعائه مقيدة؛ RPC القديم يحتفظ بحماية engine_validate.

## الاختبارات المنفذة

- `PATH="$PWD/.venv/bin:$PATH" npm test`: **565 ناجحة، 0 فشل، 0 تخطٍ**؛ خط الأساس 557، والزيادة 8 اختبارات.
- اختبارات JavaScript للتطبيع والتحقق وONE_SIZE وحل الباركود وصافي 10−7=3.
- اختبارات DOM للشاشات الحقيقية: إنشاء صف مركب، تبديل المقاس مع التأكيد والإلغاء، باركود موديل دون اختيار تلقائي، وحمولة حفظ منظمة عبر RPC واحد.
- اختبارات الإيصال بعرضي 58/80mm للنص وHTML، مع بقاء ONE_SIZE في هوية البيانات.
- اختبار PostgreSQL معزول بواسطة PGlite مثبت بإصدار محدد كاعتماد تطوير: تنفيذ الترحيل وRPC فعلياً على مخطط اختبار، قبول طلب قديم، ترتيب المكونات، رفض القيم غير الصحيحة والتكرار وعكس الترتيب، وفشل باركود مكرر يعيد جميع صفوف العملية. تحقق أيضاً من عدم تعديل الصف القديم.
- المخطط المحلي يحاكي حدود الاعتماد: engine_validate ومولد الباركود فيه بدائل اختبار؛ **هذا ليس اختبار RLS الكامل أو تزامن حجوزات Supabase**.
- Build ناجح باستخدام font mock محلي سابق وSupabase URL/key وهميين، بسبب قيود شبكة الخطوط. لم يتغير مصدر Tajawal الإنتاجي.
- استجابة المعاينة `/` و`/app.js`: HTTP 200، وخادمها مربوط بـ0.0.0.0:3000.

## المعاينة المحلية

الشاشات الفعلية مع backend محلي مؤقت بلا مفاتيح Live، وإعادة تحميل الصفحة تعيد البيانات التجريبية. لا تؤكد بيعاً نهائياً؛ إيصال/تنبيهات المعاينة تستعمل بدائل اختبار.

أمثلة مضافة إلى الكتالوج:

| المثال | باركود الموديل | باركود التركيبة |
|---|---|---|
| حقيبة بلون أسود ومقاس موحد | 200000000200 | 200000000201 |
| حقيبة بلون أبيض/أسود ومقاس موحد | 200000000300 | 200000000301 |
| قميص بلون أبيض/أزرق ومقاسي M وL | 200000000400 | 200000000401 و200000000402 |

كل تركيبة من هذه الأمثلة كمية 10 ومحجوز 7. افتح الكاشير من شريط المعاينة، أو شاشة إضافة المنتج لإنشاء مثال مؤقت، أو الملصقات لاختيار المنتج وتجربة العرض.

## ما لم يُختبر أو يُطبّق

- لا تنفيذ Phase 3 على قاعدة Supabase الحقيقية، ولا اختبار أدوار/مستأجرين على مخطط Supabase كامل بعد الترحيل، ولا اختبار تزامن جديد متعدد الاتصالات. هذه بوابة قبول لازمة قبل النشر وليست نجاحاً مستنتجاً من PGlite.
- لا اختبار متصفح بصري آلي أو جلسة Live موثقة أو جهاز HID فعلي أو طابعة فعلية أو PWA/Push.
- لم تُعدّل جميع شاشات المتجر/الإدارة الثانوية لترجمة ONE_SIZE؛ نطاق العرض المراجع هو إضافة المنتج وPOS وطباعة الباركود والإيصال. قد تعرض شاشات أخرى الكود التقني إلى حين مراجعتها.

## خطة التطبيق والتراجع الآمن — تحتاج موافقة

1. مراجعة المعاينة وتقييم تجربة اختيار المكونات أولاً.
2. تجهيز قاعدة Supabase معزولة تحمل مخطط المرحلتين السابقتين، وإجراء اختبارات RLS والأدوار وعزل المستأجر والحجز المتزامن والباركودات القديمة بعد إضافة 027. لا تتجاوز هذه البوابة بادعاء أن محاكاة PostgreSQL بديل كامل.
3. بعد النجاح والموافقة: التقاط baseline/نسخة احتياطية وفق سياسة المشروع، ثم تطبيق 027 بمعاملة محدودة المهلة، ثم نشر الواجهة؛ لا تُنشر الواجهة التي تطلب العمود قبل وجوده.
4. smoke test موثق ومصرح به، دون تحويل تجارب الكتابة إلى بيانات تجارية غير متفق عليها.
5. التراجع المفضل عند مشكلة واجهة: تعطيل إدخال الميزة أو الرجوع لإصدار الواجهة السابق **مع إبقاء العمود والبيانات وRPC المتوافق**. لا DROP COLUMN ولا حذف تركيبات جديدة ولا تغيير باركوداتها.
6. إذا لزم تعديل RPC، استخدم ترحيلاً تصحيحياً يحافظ على قراءة/حفظ الألوان المنظمة؛ الرجوع الأعمى لدالة Phase 2 قد يفقد المكونات عند الإدخال، وليس خطة تراجع مقبولة.

## تحديث: التفويض بمعاينة Vercel المعزولة

بعد التقرير الأول، وافق المستخدم صراحة على Commit وPush للفرع الحالي ونشر Preview وهمي فقط. لا يوجد تفويض بترحيل Live أو نشر Production.

- أُضيف `vercel.json` خاص بمراجعة هذا الفرع: نشر ثلاثة أصول ثابتة فقط، دون Next API أو middleware أو وظائف خادم. لا يتم تجميع عميل Supabase؛ تُستخدم بدائل المعاينة المحلية نفسها.
- `scripts/build-phase3-preview.mjs` يرفض أي `VERCEL_ENV` غير preview؛ جُرب رفض production فعلياً، كما جُرب بناء preview ونجح.
- CSP يمنع اتصالات fetch/WebSocket بـ `connect-src 'none'`؛ الصور المحلية المرفوعة تبقى blob في ذاكرة المتصفح. لا أسرار ضمن الأصول، ولا حفظ دائم للبيانات.
- لا ينبغي استخدام إعداد Vercel التجريبي هذا لنشر التطبيق الحقيقي مستقبلاً؛ يجب استبداله بإعداد التطبيق الطبيعي عند الموافقة على الإنتاج، وبعد بوابات قبول قاعدة البيانات.
- إعداد المشروع وقت الفحص: فرع الإنتاج main، والفرع الحالي مختلف، وإنشاء deployments التلقائي معطل. حماية SSO للمعاينات مفعلة ولم تُغيّر.
- أعيدت الاختبارات قبل الحفظ: 565 ناجحة دون فشل أو تخطٍ. رابط المعاينة وحالتها يبلّغان في رسالة التسليم بعد التحقق من Vercel.
